The Daily Pipeline, Step by Step

This portal is automatically updated. Every day at 05:00 UTC, a GitHub Actions workflow pulls the latest upstream data, runs a complete intervention-aware SIRD analysis, writes a JSON file consumed by the interactive front-end, and deploys the whole site to GitHub Pages. This document explains every step and the statistical reasoning behind it.

Step 1 — Data Acquisition

The upstream repository (webbegole/ebola-bundibugyo-tracker-2026) maintains a CSV of daily case reports. The workflow clones that repository to a temporary folder and copies data/timeseries.csv into the working directory. This guarantees that every analysis starts from the exact same data snapshot that other researchers can verify.

Columns used:

  • report_date — calendar date of the report.
  • confirmed_global — cumulative confirmed cases.
  • confirmed_deaths_global — cumulative confirmed deaths.
  • recovered_global — cumulative recoveries.

Step 2 — Data Wrangling and Quality Control

  • Date parsing — dates coerced to R's Date type.
  • Column normalization — names lowercased and standardized.
  • Duplicate removal — when the same date appears twice, the row with the latest source_timestamp is kept.
  • Derived columns — active cases (confirmed − deaths − recovered), CFR (100 × deaths / confirmed), and daily incidence (day-over-day differences).

Only confirmed cases are modelled. Suspected cases are excluded because reporting practices for suspected cases vary widely between sources, which would introduce systematic bias into the coefficient estimates.

Step 3 — Parameter Estimation with Interventions

The model now estimates five parameters, not three:

  • \(\beta_0\) — initial transmission rate (before interventions).
  • \(\gamma\) — recovery rate.
  • \(\mu\) — mortality rate.
  • \(k\) — intervention decay rate.
  • \(\tau_{\text{start}}\) — intervention start day (from first case).

The estimation uses non-linear least squares with the objective function:

SSE(β0, γ, μ, k, τ, I0) = Σ [observed_cumulative(t) − predicted_cumulative(t)]²

where predicted_cumulative is \(I(t) + R(t) + D(t)\) from the SIRD integration with \(\beta(t) = \beta_0 e^{-k(t-\tau)}\). The optimizer is optim() with L-BFGS-B, and parameters are log-reparameterized to enforce positivity. The intervention parameters are derived directly from the observed slowdown — the model figures out when the curve started to bend and how fast it bent.

Step 4 — Train / Test Split

The observation window is split chronologically:

  • Training window (first 80%): used to fit all five parameters plus \(I_0\).
  • Test window (last 20%): held out entirely. The fitted model is evaluated on data it has never seen.

This split is essential. A model that fits only its training data tells you nothing about real-world predictive skill. The test window is the closest available proxy for "would this model have predicted the near future correctly?" — which is precisely the use case in a real outbreak.

Step 5 — Statistical Validation

Three metrics are computed on both windows:

  • RMSE — Root Mean Squared Error; penalizes large errors; reported in same units as cases.
  • MAE — Mean Absolute Error; average absolute deviation; easier for non-specialists to interpret.
  • R² — Coefficient of determination; 1 is perfect, 0 is no better than the mean, negative values mean the model is worse than predicting a constant.

A well-fitted intervention-aware model should have a positive training R² (typically above 0.8) and a test R² that does not collapse to strongly negative. If the test R² is much worse than the training R², the model is overfitting and the projection should be treated with caution.

Step 6 — Anchored Projection

Once parameters are estimated, the SIRD system is re-anchored at the state of the last observation and integrated forward for 14 days. The β(t) decay continues into the projection — the model does not assume interventions suddenly stop. Anchoring is critical. If the projection simply continued from the model's fitted state on the last training day, it could jump discontinuously at the boundary. Anchoring guarantees visual continuity between the observed curve and the forecast.

Step 7 — Report and Deployment

The analysis produces three artefacts:

  • data/ebola_data.json — structured output consumed by the portal's interactive charts.
  • reports/dashboard.html — a self-contained R Markdown report with all tables and static charts, including the fitted β(t) trajectory and the model performance metrics.
  • data_cache.csv — a cleaned snapshot of the data, committed for reproducibility.

The GitHub Actions workflow assembles all files into _site/ and publishes the result to GitHub Pages.

Step 8 — Reproducibility Guarantees

  • The upstream data snapshot is fetched fresh every run.
  • R packages are installed from a locked, cached library.
  • The JSON output is deterministic given the same input.
  • Every artefact is versioned in the repository history.

How to Reproduce Locally

# 1. Fetch the latest upstream data
git clone https://github.com/webbegole/ebola-bundibugyo-tracker-2026
cp ebola-bundibugyo-tracker-2026/data/timeseries.csv ./downloaded_timeseries.csv

# 2. Run the analysis
Rscript incremental_fetch.R

# 3. Render the R Markdown report
Rscript -e 'rmarkdown::render("dashboard.Rmd", 
            output_file = "reports/dashboard.html")'

# 4. Serve the portal locally
python3 -m http.server 8000

Then open http://localhost:8000 in a browser.

Why This Workflow Matters

In an Ebola outbreak, the value of a model is not in its elegance but in its timeliness and reliability. By including the intervention effect, by validating against a held-out window, and by anchoring the forecast to the last observed state, this pipeline ensures that:

  • The forecast reflects what is actually happening, not what would have happened if nothing had been done.
  • The intervention speed and timing are derived from data, not assumed.
  • The performance metrics are visible and honest.
  • Every number displayed can be traced back to a specific code path and a specific data snapshot.
