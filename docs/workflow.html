The Daily Pipeline, Step by Step

This portal is not manually updated. Every day at 05:00 UTC, an automated GitHub Actions workflow pulls the latest upstream data, runs a complete SIRD analysis, writes a JSON file consumed by the front-end, and deploys the whole site to GitHub Pages. This document explains every step and the statistical reasoning behind it.

Step 1 — Data Acquisition

The upstream repository (webbegole/ebola-bundibugyo-tracker-2026) maintains a CSV of daily case reports. The workflow clones that repository to a temporary folder and copies data/timeseries.csv into the working directory. This guarantees that every analysis starts from the exact same data snapshot that other researchers can verify.

The columns used are:

  • report_date — the calendar date of the report.
  • confirmed_global — cumulative confirmed cases.
  • confirmed_deaths_global — cumulative confirmed deaths.
  • recovered_global — cumulative recoveries.

Step 2 — Data Wrangling and Quality Control

The raw CSV is cleaned to ensure that downstream modelling is not contaminated by duplicates or missing values:

  • Date parsing — all dates are coerced to R's Date type with a common format.
  • Column normalization — names are lowercased and standardised.
  • Duplicate removal — when the same date appears multiple times, the row with the most recent source_timestamp is kept.
  • Derived columns — the model computes active cases (confirmed − deaths − recovered), CFR (100 × deaths / confirmed), and daily incidence (the difference in cumulative cases day-over-day).

Only confirmed cases are modelled. Suspected cases are excluded because reporting practices for suspected cases vary widely between sources, which would introduce systematic bias into the coefficient estimates.

Step 3 — Parameter Estimation

The three biological coefficients — transmission (\(\beta\)), recovery (\(\gamma\)), and mortality (\(\mu\)) — are estimated by non-linear least squares. The objective function is:

SSE(β, γ, I₀) = Σ [observed_cumulative(t) − predicted_cumulative(t)]²

where the model's cumulative output is I(t) + R(t) + D(t). The optimizer is optim() with the L-BFGS-B method, which allows box constraints on the parameters. Log-reparameterization guarantees that all proposed values are positive.

The fitted coefficients in the latest run are written to the JSON file and displayed in the "Biological Coefficients" cards of the portal.

Step 4 — Train / Test Split

The observation window is split chronologically:

  • Training window (first 80%): used to fit \(\beta, \gamma, \mu\) and the initial infectious count \(I_0\).
  • Test window (last 20%): held out entirely. The fitted model is evaluated on this window to measure predictive skill on data it has never seen.

This split is essential. A model that fits only its training data is meaningless. The test window is the closest available proxy for "would this model have predicted the near future correctly?" — which is the primary use case in a real outbreak response.

Step 5 — Statistical Validation

Three validation metrics are computed on both windows:

  • RMSE — Root Mean Squared Error. Penalises large errors; reported in the same units as the case counts.
  • MAE — Mean Absolute Error. Average absolute deviation; easier to interpret for non-specialists.
  • R² — Coefficient of determination. Fraction of variance explained; 1 is perfect, 0 is no better than the mean, and negative values mean the model is worse than predicting a constant.

These metrics are displayed in the "Model Performance" box on the predictive chart, so readers can judge for themselves how much confidence to place in the forecast.

Step 6 — Projection

Once parameters are estimated, the SIRD system is re-anchored at the state of the last observation and integrated forward for 14 days. Anchoring is critical: without it, the projection can jump discontinuously at the boundary between data and forecast.

The projected curve is therefore guaranteed to begin exactly where the observed curve ends — a small but crucial detail that distinguishes a professionally presented forecast from an unreliable one.

Step 7 — Report and Deployment

The analysis produces three artefacts:

  • data/ebola_data.json — structured output consumed by the portal's interactive charts.
  • reports/dashboard.html — a self-contained R Markdown report with all tables and static charts.
  • data_cache.csv — a cleaned snapshot of the data, committed for reproducibility.

The GitHub Actions workflow then assembles all files into _site/ and publishes the result to GitHub Pages. The whole process is automatic and runs daily.

Step 8 — Reproducibility Guarantees

  • The upstream data snapshot is fetched fresh every run.
  • R packages are installed from a locked, cached library to avoid version drift.
  • The JSON output is deterministic given the same input CSV.
  • Every artefact is versioned in the repository history, so any analysis can be audited later.

How to Reproduce Locally

The entire pipeline can be reproduced on any machine with R installed:

# 1. Fetch the latest upstream data
git clone https://github.com/webbegole/ebola-bundibugyo-tracker-2026
cp ebola-bundibugyo-tracker-2026/data/timeseries.csv ./downloaded_timeseries.csv

# 2. Run the analysis
Rscript incremental_fetch.R

# 3. Render the R Markdown report
Rscript -e 'rmarkdown::render("dashboard.Rmd", 
            output_file = "reports/dashboard.html")'

# 4. Serve the portal locally
python3 -m http.server 8000

Then open http://localhost:8000 in a browser to see the same site that GitHub Pages hosts.

Why This Workflow Matters

In an Ebola outbreak, the value of a model is not in its elegance but in its timeliness and reliability. By automating the entire chain — data ingestion, cleaning, fitting, validation, projection, and publication — this pipeline ensures that:

  • The portal always shows the most recent data.
  • The model is refitted every day to the newest observations.
  • The forecasts and their performance metrics are always transparent.
  • Every number displayed can be traced back to a specific code path and a specific data snapshot.
