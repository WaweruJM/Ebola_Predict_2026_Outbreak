The Daily Pipeline, Step by Step

This portal is not manually updated. Every day at 05:00 UTC, a GitHub Actions workflow pulls the latest upstream data, runs the SIR model, exports a JSON file, renders an R Markdown report, and publishes the whole site to GitHub Pages. Here is the entire workflow explained.

Step 1 — Data Preparation

The upstream repository (webbegole/ebola-bundibugyo-tracker-2026) publishes a CSV of daily case reports. The workflow clones that repository to a temporary folder and copies data/timeseries.csv into the workspace. All further analysis is done against that snapshot — no external API calls, fully reproducible.

Step 2 — Data Wrangling

The raw CSV contains cumulative confirmed cases, confirmed deaths, and recoveries. The R script cleans the data:

  • Parses dates unambiguously.
  • Normalises column names (lowercase, snake_case).
  • Removes duplicate daily rows, keeping the one with the most recent source timestamp.
  • Computes derived columns: active cases, case fatality rate, daily incidence.

Only confirmed cases are used in modelling. Suspected cases are excluded because their reporting is far more variable across sources.

Step 3 — Parameter Estimation

The SIR parameters (β, γ, μ) are estimated by non-linear least squares. The objective function is: 

SSE(β, γ, I₀) = Σ [observed_cumulative(t) − predicted_cumulative(t)]²

where the model's cumulative output is I(t) + R(t) + D(t). The optimisation uses optim(method = "L-BFGS-B") with logarithmic reparameterisation to enforce positivity and box constraints to prevent physically impossible estimates.

Step 4 — Train / Test Split

The observation window is divided chronologically:

  • Training (first 80 %): Used to fit β, γ, and I₀.
  • Testing (last 20 %): Held out entirely. The fitted model is evaluated on this window to measure predictive skill on data it has never seen.

This is essential for honest performance metrics. A model that fits only its training data is useless — the test window reveals whether the estimated parameters generalise.

Step 5 — Model Performance

Three metrics are reported for each window:

  • RMSE — Root Mean Squared Error. Penalises large errors; same units as the data.
  • MAE — Mean Absolute Error. Average absolute deviation; easier to interpret.
  • R² — Coefficient of determination. Fraction of variance explained; 1 is perfect, 0 is no better than the mean, negative means worse than the mean.

Step 6 — Projection

Once parameters are estimated, the ODE system is re-anchored at the state of the last observation and integrated forward for 14 days. Anchoring at the last observed state guarantees the projection begins exactly where the data ends, with no visible discontinuity.

Step 7 — Export and Deploy

The script writes data/ebola_data.json containing all cards, chart series, coefficients, zones, and slider defaults. The R Markdown report is rendered to reports/dashboard.html. The workflow then assembles the deployable site, publishes it to the gh-pages branch, and GitHub Pages serves the new version within a minute.

Reproducibility Guarantees

  • The upstream data snapshot is fetched fresh every run.
  • R packages are installed from a locked, cached library.
  • The JSON output is deterministic given the same input CSV.
  • Every artefact is versioned in the repository history.

How to Reproduce Locally

# 1. Fetch the latest upstream data
git clone https://github.com/webbegole/ebola-bundibugyo-tracker-2026
cp ebola-bundibugyo-tracker-2026/data/timeseries.csv ./downloaded_timeseries.csv

# 2. Run the analysis
Rscript incremental_fetch.R

# 3. Render the report
Rscript -e 'rmarkdown::render("dashboard.Rmd",
            output_file = "reports/dashboard.html")'

# 4. Serve the portal
python3 -m http.server 8000

Then open http://localhost:8000 in your browser.
